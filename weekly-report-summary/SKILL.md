# 产品部周报汇总

## 调用方式

标准调用：`$weekly-report-summary`

触发短语：`【产品部周报汇总】`、`产品部周报汇总`

除非用户明确指定其他模板，否则 `$weekly-report-summary` 等同于：`$weekly-report-summary，按"产品部周报汇总"模板执行`

收到触发指令后，立即使用以下默认参数执行，不要再向用户确认输入参数，除非必要的钉钉文档/文件夹无法访问。

---

## 一、Skill 功能概述

本 Skill 用于处理产品部收到的多份周报，完成两件事：

1. **归档个人周报**：将每份收到的周报完整归档为独立的钉钉文档
2. **生成部门周报汇总**：基于指定的主管周报模板，从归档的周报中提取、清洗、统计、汇总，生成一份部门级周报

适用场景：
- 查询指定日期范围内收到的周报
- 归档每份周报为钉钉文档
- 排除指定人员的周报
- 以主管周报作为结构模板
- 从其他周报中提取内容进行汇总
- 额外解析吕夏苗个人周工作总结文档，填充「二、本周个人工作总结」（第 0-3 部分严格复制钉钉周工作总结，第 4 部分来自 AI 工具一周使用总结）

## 二、Skill 全局规则

### 2.1 输入参数

对于固定预设 `产品部周报汇总`，不再暂停确认以下输入，直接使用默认值执行：

| 参数 | 默认值 |
|------|--------|
| 查询日期范围 | 当前会话日期（北京时间）当天的收到周报 |
| 归档目标文件夹 | `https://alidocs.dingtalk.com/i/nodes/D1YKdxGX7EqVQZe2y71ZJe4QrZk95AzP` |
| 汇总模板文档 | `产品部部门周报汇总（模板）`：https://alidocs.dingtalk.com/i/nodes/Obva6QBXJw9lAGpdF2vXqv16Wn4qY5Pr |
| 排除人员 | 吕夏苗的周报不归档、不作为部门汇总输入 |
| 允许的发件人 | `孙圣宇`、`张永翔`、`邓智泳`、`王俊秀` |

固定预设 `产品部周报汇总` 已确认最终版模板文档为 `产品部部门周报汇总（模板）`（nodeId: `Obva6QBXJw9lAGpdF2vXqv16Wn4qY5Pr`）。每次执行必须优先以该模板文档为结构来源，不得从主管周报或其他历史汇总文档重新生成模板结构。

### 2.2 工具优先级与兜底规则

执行本 Skill 时，必须优先使用可用的钉钉 MCP 服务完成任务；只有当当前会话没有对应 MCP 服务、MCP 服务能力不满足该步骤、或 MCP 调用明确失败且无法通过同类 MCP 工具继续时，才允许使用 `dws` 兜底。

**MCP 优先范围：**
- 周报/日志列表查询：优先使用 `dingding_worklog_mcp` 的收到日志列表能力
- 单篇周报详情读取：优先使用 `dingding_worklog_mcp` 的日志详情能力
- 钉钉文档块读取、结构校验、块删除、追加/覆盖写入、导出：优先使用 `dingtalk_doc_mcp` 或同等钉钉文档 MCP
- 文件夹、云盘、知识库节点、同名文档查找、删除、创建、模板复制等操作：如存在对应 MCP 服务，必须优先 MCP

**dws 兜底前置要求：**
- 只有在明确记录“对应 MCP 不存在/不可用/能力不满足”的原因后，才能使用 `dws`
- 使用 `dws` 遇到认证、授权链接、scope 缺失、token 写入失败时，必须立即向用户暴露阻塞和授权方式，不得静默重试或假装继续
- 使用 `dws` 产生的长输出默认存在截断风险，除非已完成下方硬性校验

**dws 兜底硬性校验：**
1. 长输出必须分页或分段读取；单次输出接近工具限制、缺少尾部结构或无法确认完整性时，默认不可信，必须继续分段读取
2. 每个表必须统计源行数和汇总行数；至少记录表名、来源周报、源行数、纳入行数、排除行数
3. 每个模板章节必须做存在性检查；尤其检查 `重点项目`、`7. 组长工作总结`、`二、本周个人工作总结`
4. 每条纳入规则必须能解释来源和原因；对 `重点项目`，每行需能说明其来自哪位组长周报的哪个源表格
5. 输出接近限制时默认不可信，必须通过分页读取、关键词复查、`rowSize/cells.length` 校验或同等结构化方式确认完整

### 2.3 时区规则

所有日期和日边界逻辑必须使用北京时间：`Asia/Shanghai`（`UTC+08:00`）。

适用于：
- 判断「今天」「昨天」等相对日期
- 将钉钉毫秒时间戳转换为日历日期
- 选择回退日期
- 显示最终的 `汇总日期` 和 `源周报日期`

**`汇总日期` 规则：**
- 永远是当前执行日期的北京时间
- 不是周报发送日期，也不是内容覆盖日期
- 即使源周报和主管周报是更早发送的，`汇总日期` 仍用当天

**`源周报日期` 规则：**
- 必须从选中的源周报实际时间戳（转换为 `Asia/Shanghai`）推导
- 不得从回退锚点日期、查询窗口起始日期、周报标题中的周标签或 UTC 日期推导
- 如果所有选中的在范围周报落在同一个北京日期，显示该确切日期
- 如果跨越多个北京日期，显示明确的日期范围

**禁止：** 当源时间戳意图为中国标准时间时，绝不能从 UTC 日边界推导报告日期。

### 2.4 强制执行规则

#### 2.4.1 必须真正汇总

仅复制或重建模板文档本身永远不够。每次执行必须产生从选中的个人周报真正推导出的部门汇总。

**强制执行基线：**
1. 先识别在范围内的个人周报
2. 再获取并完整阅读每份在范围内的周报
3. 再从每份源周报中提取实际的段落、列表和表格数据
4. 再从提取的源周报计算部门级汇总
5. 再将计算结果写回汇总文档，同时保留已批准的模板结构和呈现

**禁止的捷径：** 不得将 `产品部部门周报汇总（模板）` 或任何之前的汇总文档直接复制后声称为已完成，除非其内容已针对当前选中的源周报重新验证和更新。

#### 2.4.2 来源可追溯规则

生成的部门汇总必须可追溯到来源：

- 汇总中每个填充的段落、列表项和表格行必须来自一份或多份选中的在范围个人周报（除非是明确的模板元数据）
- 每个聚合数值表格必须可从选中的源周报复现
- 如果一个值无法追溯到选中的源周报，不得保留为汇总结果

**执行要求：**
- 维护每个汇总章节与其来源周报之间的映射关系
- 将选中的个人周报视为本次运行的真值输入集
- 复用已复制的模板文档时，在保留内容之前，必须针对当前源周报验证每个非样式敏感的汇总块
- 来源映射、纳入原因、冲突判断、校验状态只用于内部核验和当前会话最终报告；不得为了追溯性在产出文档 `产品部部门周报汇总` 的表格中新增 `来源`、`纳入原因`、`校验状态`、`备注` 等模板外字段
- 产出文档必须保持模板原有列名、列数、列顺序和章节格式；除非模板本身已有对应字段或用户明确要求，否则不得向部门周报正文添加给操作者看的说明性字段

#### 2.4.3 来源冲突解决规则

不同源周报可能包含重叠的汇总数据且数值不一致。此时：

1. 优先选择明确作为该指标权威来源的最具体表格或章节
2. 优先选择内部自洽（明细行与合计匹配）的源表格
3. 不得静默将矛盾数值合并为编造的折中值
4. 如果为某个冲突指标选择了某一来源而非另一个，在最终响应中记录该选择
5. 如果无法有把握地解决冲突，停止并暴露歧义，而不是假装数据已确定

#### 2.4.4 回退日期规则

如果当前目标日没有收到周报，且当天也没有发出的主管周报，不要立即停止。使用以下回退：

1. 找到当前预设或工作流范围内最近一个有在范围收到周报的日期
2. 找到匹配同一工作流范围的最近一份已发出的主管周报
3. 使用这些最近的在范围输入运行工作流

如果只有一侧缺失，只回退缺失的一侧。

**必须在响应中明确说明回退日期**，让用户知道实际使用了哪个源周报日期。此回退日期仅用于来源选择，不得替换 `汇总日期`。`汇总日期` 仍必须使用当前北京时间日历日期。也不得将回退锚点日期直接复制为 `源周报日期`，`源周报日期` 仍必须从选中周报的实际北京 时间戳推导。

#### 2.4.5 模板来源规则

部门周报格式必须遵循指定的模板来源：
- 固定预设 `产品部周报汇总` 已确认最终版模板文档为 `产品部部门周报汇总（模板）`（nodeId: `Obva6QBXJw9lAGpdF2vXqv16Wn4qY5Pr`），每次执行必须优先使用该模板文档作为结构来源
- 如该模板文档不可访问，先尝试回退到同名的历史汇总文档；仍不可用时，才使用指定的主管周报作为结构模板，并在最终响应中说明

**必须：**
- 保留最终版模板文档的主章节结构
- 尽可能保留其子章节层级
- 将其他收到的周报映射到最终版模板结构中
- 不得自行发明新的部门周报大纲，除非用户明确要求
- 最终版模板已删除 `其他重点项目` 模块，并将原 `工作量30及以上、重点以及C端产品需求明细` 模块改为 `重点项目`，汇总文档必须严格以该结构为准

本 Skill 是全局可复用的。不要硬编码吕夏苗，除非当前任务明确使用吕夏苗的主管周报作为模板。

#### 2.4.6 表格更新回退方案

当钉钉块级表格更新失败时，使用以下回退：
1. 定位现有块
2. 删除旧块
3. 在正确位置插入新块
4. 重新读取附近块以验证位置

#### 2.4.7 删除重建与时间校验规则

对于固定预设 `产品部周报汇总`，归档个人周报和生成部门汇总文档时，必须优先执行删除重建，而不是仅更新旧文档内容。

**强制规则：**
- 如果目标文件夹中已存在同名个人周报文档，必须先删除旧文档，再创建新文档。
- 如果目标文件夹中已存在同名部门汇总文档，必须先删除旧文档，再创建新文档。
- 不得仅通过块级更新、全文覆盖或追加内容来代替删除重建，除非钉钉文档 API 明确不支持删除/创建，或删除操作会导致不可接受的模板样式损失。
- 如因 API 限制、权限限制或样式保真风险不能删除重建，必须在最终响应中明确说明：哪些文档没有删除重建、原因是什么、实际采用了哪种替代方式。
- 执行完成后，必须验证目标文件夹中文档的更新时间或创建状态，确保新建/重建动作可被用户从列表时间上识别。
- 当用户指出列表更新时间仍为旧时间时，必须视为删除重建规则未满足，不能声称流程已完整完成。

## 三、查询 & 归档个人周报

### 3.1 查询规则

1. 使用北京时间的日边界查询指定日期范围内的候选收到周报
2. 周报列表查询和单篇周报详情读取必须优先使用钉钉周报/日志 MCP；只有 MCP 不存在、不可用或能力不满足时，才允许使用 `dws` 兜底
3. 在归档之前，先识别哪些周报属于当前工作流或预设的范围
4. 如果未找到在范围的周报，对限定的工作流应用回退日期规则，而非对所有收到周报应用
5. 获取每份在范围结果的周报详情，并将所有时间戳归一化为 `Asia/Shanghai` 后再比较日期
6. 获取周报详情后必须检查关键章节是否存在：`一、本周工作总结`、`二、本周个人工作总结`、`三、下周工作计划`、`四、需要协调与帮助`
7. 对于 `产品部周报汇总`，只有 `孙圣宇`、`张永翔`、`邓智泳`、`王俊秀` 发送的周报属于在范围
8. 发件人白名单优先级高于基于日期的回退或邮箱共收
9. 标题匹配仅为辅助检查；如果发件人不在白名单内，默认排除该周报
10. 排除不相关部门的周报（如标题含 `（科研服务部）`），除非用户明确要求跨部门处理

**发件人范围：**

仅以下发件人默认允许进入 `产品部周报汇总`：

- `孙圣宇`
- `张永翔`
- `邓智泳`
- `王俊秀`

如果周报来自其他发件人，排除在归档生成和部门汇总输入之外，除非用户明确扩展范围。

吕夏苗的周报是特殊例外：当最终版模板文档不可用时，可作为回退模板来源，但不得归档为个人周报文档，也不得计入部门汇总输入。

### 3.2 归档规则

在识别在范围的周报并获取详情后，先归档再汇总。**不要**默认归档当天的所有周报。

**默认归档行为：**
- 仅归档被选入工作流在范围个人周报集合的周报
- 主管周报、模板来源周报和明确排除的周报不得归档为个人周报文档
- 对于固定预设 `产品部周报汇总`，吕夏苗的周报不得归档，也不得作为汇总输入
- 归档文档的同名查找、删除、创建、读取回验必须优先使用钉钉文档/云盘/知识库 MCP；只有缺少对应 MCP 能力时才使用 `dws` 兜底
- 每份周报一个钉钉文档
- 文档名称 = 周报名称
- 内容必须完整复制，不做摘要、压缩或改写
- 如果目标文件夹中已存在同名个人周报文档，先删除旧文档再创建新文档
- 使用删除再创建而非覆盖（当用户需要新创建时间戳时）
- 创建部门汇总文档前，如目标文件夹中已存在同名汇总文档，先删除旧文档再创建新文档
- 如果回退日期的邮箱是混合的，仅归档被选入预设范围的周报
- 不要批量归档当天所有收到的周报

## 四、部门周报汇总

### 汇总总体规则

- 使用最终版部门汇总模板文档作为首选结构来源；如不可用，再使用主管周报作为结构模板
- 读取模板、复制模板、创建汇总文档、编辑文档块、删除文档块、读回校验必须优先使用钉钉文档 MCP；只有 MCP 不存在、不可用或能力不满足时才使用 `dws` 兜底
- 完整阅读每份选中的源周报并提取实际的段落、列表和表格
- 构建所有主要章节和汇总表格的来源-汇总映射
- 归一化选中的源周报中重复的分类、重叠的行和表格合计
- 从提取的源周报重新计算部门汇总内容，而非默认信任之前的汇总输出
- 复制的模板文档在汇总内容针对当前源周报重新计算或重新验证之前，不得视为已完成
- 写入后必须用文档 MCP 或同等结构化方式读回校验，至少验证章节存在性、关键表 `rowSize`/`cells.length`、关键漏项关键词和模板列结构；来源追踪在内部记录和最终报告中说明，不得通过新增输出列实现

#### 4.0.1 模板表格保真规则

对于主管周报模板中已存在的任何表格：
- 在部门汇总中保留为真正的表格
- 严格保留模板原有列名、列数和列顺序；不得自行新增 `来源`、`纳入原因`、`校验状态` 等模板外列
- 不得将模板表格折叠为纯文本、项目符号或段落式汇总
- 如果模板在同一父章节下有多个同级表格，保留所有表格，除非用户明确要求删除
- 如果已确认的最终版模板文档存在，所有表格保真规则中的「模板」均指该最终版模板文档
- 如果没有某个保留模板表格的源数据：保留表格结构，行留空、填零或与模板保持一致，不得仅因某些值为空就删除表格

当部门汇总渲染到钉钉文档时，使用固定预设 `产品部周报汇总` 时必须应用以下合并单元格呈现规则。这些是汇总文档的呈现规则，即使底层源值稀疏也应保留。

**A. `创新ToB增收明细`**
- 保留为真正的表格
- 包含行：`伏羲慧眼`、`AI电子相册`、`统战系统`、`ALLiN1`、`其他`
- 在确认的显示变体中：
  - `指标` 从 `AI电子相册` 到 `其他` 纵向合并
  - `完成度` 从 `AI电子相册` 到 `其他` 纵向合并

**去 AI 味规则（需严格执行）：**

核心原则：**读起来像主管自己写的周报，不像 AI 模板生成的文本。**

具体含义：
- "去 AI 味" ≠ 去掉 AI 工具名称。第 4 部分本身就是 AI 工具应用总结，保留工具名和具体场景是合理的——读者需要知道"用什么做了什么"才能判断创新价值。
- "去 AI 味" = 去掉 AI 生成文本的**模板感、机械感和流水账感**，让人读不出是机器写的。

禁止的写作特征（即"AI 味"来源）：
- 每条都以同样的句式开头（如全部用"通过XX完成了YY"的模板句式）
- 干巴巴的操作流水账（"运行了XX脚本 → 配置了XX参数 → 输出了XX结果"）
- 缺乏具体场景和判断（"优化了工作流""提升了效率"——什么工作流？效率从多少提到多少？）
- 过度工整的排比和四字短语堆砌
- 用"该"代替"这个"、用"予以"代替"给"等公文腔

应追求的写作特征（即"人味"）：
- 自然的叙述节奏，有长句有短句
- 有具体场景（"以前XX要花半天，现在XX分钟内搞定"）
- 有个人判断和取舍（"试了A方案但效果不好，改用B方案跑通了"）
- 像在跟同事口头汇报，不像是照着稿子念
- 关键动作和数据经得住追问
- **精炼不啰嗦**：每条 1-2 句话，只写做了什么和结果是什么，不铺垫、不解释、不展开背景。不要写成"本周做了什么，主要解决了XX问题，具体来说就是XXX，以前是YYY现在是ZZZ"这种层层展开的段落式写法。

第 4 部分特别规则：
- 可以且应当提到具体 AI 工具——这是"AI 应用总结"，不说工具名失去价值
- 但要避免写成"XX工具→做了YY"的机械清单
- 好的写法：交代背景（为什么用）、做了什么（具体成果）、价值是什么（对比从前）
- 来源文档（AI工具一周使用总结）本身包含工具名和技术细节，转化时要提取核心创新点和可复用成果，重新组织为自然的叙述

第 0-3 部分规则：
- 来自 `钉钉一周工作总结`，必须严格按对应章节复制原文；即使包含 AI 相关内容、会议名称、具体时间、来源说明或较长描述，也不得删除、改写、压缩或转移

**内容分类边界规则：**
- **学习与创新（第 4 部分）**：个人学习、个人能力提升、个人创新实践。仅限个人层面的新尝试和方法沉淀。
- **管理与协作（第 3 部分）**：组织团队活动、安排会议/竞赛/培训、制定团队计划、推进跨部门事项。凡是涉及组织他人、分配任务、制定规则的，都归入第 3 部分。
- **典型误分类案例**：
  - PPT创新竞赛 → 第 3 部分（管理与协作），不是第 4 部分（这是组织团队活动，不是个人学习）
  - 制定Q3产品规划 → 第 3 部分，不是第 4 部分
  - 组织团队培训/分享会 → 第 3 部分，不是第 4 部分

  - 个人沉淀可复用工作流 → 第 4 部分

### 6.10 markdown / jsonml 写入路径实操坑（2026-10-10 新增）

1. **中文一律写真实字符，禁止手工拼 `\uXXXX` 转义**。手工转义极易写错近形字且钉钉不报错，只在回读时才暴露：本次把「梳」`U+68B3` 误写成「梓」`U+6893`，一次性污染了 3 个段落。构造 `markdown` / `jsonml` 参数时直接书写中文。
2. **局部回读必须用 `format=jsonml`**。`get_document_content` 的 `scope`/`tags` 与 `markdown` 不兼容，传 markdown 会报 `scope/tags filtering is only supported when format=jsonml`。校验套路：`scope=outline` 校标题层级；`scope=tags&tags=p&maxDepth=1` 取全部段落及 `uuid`；`scope=range` + `startBlockId/endBlockId` 校指定区间正文。
3. **`update_document_block` 传 jsonml 时括号层级是三层**：`["p",{…},["span",{"data-type":"text"},["span",{…},"文本"]]]`，结尾必须 **3 个 `]`**（p → span → leaf）。少一层即报 `jsonml is not valid JSON: unclosed jsonArray`。
4. **`update_document_block` 存在并发写锁**：对同一文档连续下发多个块级更新会报 `unable to write to document concurrently, try later`。必须**串行调用**，失败的那一条单独重试即可成功。
5. **定向改字优于整篇重写**。发现个别字词错误时，先用 `scope=tags&tags=p` 定位受影响段落的 `uuid`，再用 `update_document_block(format=jsonml)` 只替换该段，可完整保留段内加粗分段，避免整篇重写再次引入转义风险。

### 6.12 严禁写入模板本体 + 误写回滚方法（2026-10-16 新增）

**必须按此顺序生成汇总文档，缺一步都可能写坏模板：**

1. `copy_document(nodeId=模板nodeId, targetFolderId=目标文件夹)` → 取得**新节点 ID**
2. `rename_document(新节点 ID, 产品部部门周报汇总)`
3. 之后所有 `update_document` / `insert_document_block` / `update_document_block` 一律使用**第 1 步返回的新节点 ID**

**硬性校验（写入前必须逐条确认）：**
- 目标 nodeId ≠ 模板 nodeId（模板为 `Obva6QBXJw9lAGpdF2vXqv16Wn4qY5Pr`）
- 目标 nodeId ≠ 4 份成员归档文档 / 2 份个人总结来源文档的 nodeId
- `copy_document` 返回的 `nodeId` 与传入的 `nodeId` 必须不同；若相同或未返回，先 `list_nodes` 按名称确认副本节点，再继续

**误写模板后的回滚方法（本次实证有效）：**
1. `list_doc_versions(nodeId=模板nodeId)`，取误写动作**之前**的那一版（本次误写产生 v126，回滚目标是 v125）
2. `revert_doc_version(nodeId=模板nodeId, version=125)`
3. 用 `get_document_content(format=jsonml, scope=outline)` 比对回滚后的标题层级与原始模板一致，确认恢复
4. 回滚后模板 `updateTime` 会保持在被回滚版本的原始时间，列表上不显示为「刚被修改」；但版本历史会留下误写与回滚两条记录，必须在最终报告中向用户说明

**教训：** 由 `copy_document` 拿到新 nodeId 后，应先把该 nodeId 单独记下来再写内容，不要在同一批工具调用里「复制+写入」，避免把模板 nodeId 误当作写入目标。
